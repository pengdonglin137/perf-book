## 微架构特定性能问题 {#sec:UarchSpecificIssues}

在本节中，我们将讨论影响大多数现代处理器的一些常见微架构特定问题。我称它们为微架构特定的，因为它们是由特定微架构功能的实现方式引起的。这些问题非常具体，不会经常作为主要性能瓶颈出现。通常，它们被其他更重要的性能问题稀释。因此，这些微架构特定的性能问题被认为是边缘情况，不如我们在本书中已经讨论的其他问题知名。尽管如此，它们可能导致非常不受欢迎的性能惩罚。请注意，特定问题的影响在一种平台上可能比另一种更明显。此外，请记住，下面涵盖的微架构特定问题列表并非详尽无遗。

### 内存顺序违规 {#sec:MemoryOrderViolations}

我在 [@sec:uarchLSU] 中介绍了内存排序的概念。内存重排序是现代 CPU 的一个关键方面，因为它使它们能够并行和乱序执行内存请求。加载/存储重排序中的关键元素是内存消歧，它预测让加载提前于较早的存储是否安全。由于内存消歧是推测性的，如果处理不当，它可能导致性能问题。

考虑 [@lst:MemOrderViolation] 左边的示例。此代码片段计算 8 位灰度图像的直方图，即图像中某种颜色出现的次数。除了无数其他地方之外，此代码可以在 Otsu 阈值算法[^1] 中找到，该算法用于将灰度图像转换为二值图像。由于输入图像是 8 位灰度，因此只有 256 种不同的颜色。

对于图像上的每个像素，你需要读取该像素颜色的当前直方图计数，递增它，并将其存回。这是通过内存的经典读取-修改-写入依赖。假设我们在图像中有以下连续像素：`pixels = [0xFF,0xFF,0x00,0xFF,...]` 等等。`pixels[1]` 的直方图计数的加载值来自上一次迭代的结果（`pixels[0]`）。`pixels[2]` 的直方图计数来自内存；它是独立的，可以被重排序。但同样，`pixels[3]` 的直方图计数依赖于处理 `pixels[1]` 的结果，依此类推。迭代 0、1 和 3 是依赖的，不能被重排序。

Listing: 内存顺序违规示例。

~~~~ {#lst:MemOrderViolation .cpp}
std::array<uint32_t, 256> hist;           std::array<uint32_t, 256> hist1;
hist.fill(0);                             std::array<uint32_t, 256> hist2;
int N = width * height;                   hist1.fill(0);         
for (int i = 0; i < N; ++i)       =>      hist2.fill(0);
  hist[image[i]]++;                       int N = width * height;         
                                          int i = 0;
                                          for (; i + 1 < N; i += 2) {
                                            hist1[image[i+0]]++;
                                            hist2[image[i+1]]++;
                                          }
                                          // 余数
                                          for (; i < N; ++i)
                                            hist1[image[i]]++;
                                          // 合并部分直方图
                                          for (int i = 0; i < hist1.size(); ++i)
                                            hist1[i] += hist2[i];
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

回想 [@sec:uarchLSU]，处理器不一定知道潜在的存储到加载转发，因此它必须做出预测。如果它正确预测了颜色 `0xFF` 两次更新之间的内存顺序违规，那么这些访问将被序列化。性能不会很好，但这是我们可以用初始代码期望的最好结果。相反，如果处理器预测没有内存顺序违规，它将推测地让两个更新并行运行。稍后它将识别错误，刷新流水线，并重新执行两个更新中较新的一个。这对性能非常有害。

性能将很大程度上取决于输入图像的颜色模式。具有长序列相同颜色像素的图像将比颜色不经常重复的图像性能更差。只要两个相同颜色像素之间的距离足够长，初始版本的性能就会很好。在此上下文中，"足够长"一词由乱序指令窗口的大小决定。如果在同一颜色的重复读取-修改-写入发生在几个循环迭代内，它们可能会触发排序违规，但如果它们相隔一百多个循环迭代发生则不会。

[@lst:MemOrderViolation] 右边显示了内存顺序违规问题的治愈方法。如你所见，我复制了直方图，现在像素的处理在两个部分直方图之间交替。最后，我们组合两个部分直方图以获得最终结果。这个具有两个部分直方图的新版本仍然容易出现潜在的问题模式，例如 `0xFF 0x00 0xFF 0x00 0xFF ...`。但是，通过此更改，原始最坏情况（例如 `0xFF 0xFF 0xFF ...`）将比以前快两倍。根据输入图像的颜色模式，创建四个或八个部分直方图可能是有益的。这段确切的代码出现在 Performance Ninja 课程的 [mem_order_violation_1](https://github.com/dendibakh/perf-ninja/tree/main/labs/memory_bound/mem_order_violation_1)[^2] 实验室作业中，所以请随意实验。

在少量输入图像上，我在各种平台上观察到 10% 到 50% 的加速。值得一提的是，右边的版本消耗了 1 KB 的额外内存，在这种情况下可能不是很大，但需要注意。
