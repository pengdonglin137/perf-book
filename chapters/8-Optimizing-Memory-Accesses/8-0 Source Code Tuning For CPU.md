# 第二部分：源代码调优 {.unnumbered}

\markboth{第二部分：源代码调优}{第二部分：源代码调优}

在本书的第一部分中，我们讨论了如何找到代码中的性能瓶颈。在第二部分中，我们将讨论如何通过使用底层源代码优化技术（也称为*调优*）来修复这些瓶颈。

现代 CPU 是一个非常复杂的设备，几乎不可能预测某些代码片段的运行速度。软件和硬件性能取决于许多因素，活动部件的数量太大，人类思维无法容纳。幸运的是，得益于我们在本书第一部分中讨论的所有性能监控功能，从 CPU 的角度观察代码如何运行是可能的。我们将广泛依赖本书前面学到的方法和工具来指导我们的性能工程过程。

在非常高的层次上，软件优化可以分为五类。

* **算法优化**。分析程序中使用的算法和数据结构，看看是否能找到更好的。例如：使用快速排序而不是冒泡排序。
* **并行化计算**。如果算法高度可并行化，使程序多线程化，或考虑在 GPU 上运行它。目标是同时做多件事。并发已经在硬件和软件堆栈的所有层中使用。例如：将工作分配给多个线程；在数据中心的许多服务器之间平衡负载；使用异步 IO 避免在等待 IO 操作时阻塞；保持多个并发网络连接以重叠请求延迟。
* **消除冗余工作**。不做不需要或已经做过的工作。例如：利用使用更多 RAM 来减少必须使用的 CPU 和 IO（缓存、查找表、压缩）；预计算编译时已知的值；将循环不变计算移到循环外；通过引用传递 C++ 对象以消除按值传递导致的过多复制。
* **批处理**。聚合多个类似操作并一次性完成，从而减少重复执行操作的开销。例如：发送大的 TCP 数据包而不是许多小的；分配一大块内存而不是为数百个小对象分配空间。
* **排序**。重新排列算法中操作的顺序。例如：更改数据布局以启用顺序内存访问；根据类型对 C++ 多态对象数组进行排序以允许更好的虚函数调用预测；将热函数分组并将其放置在二进制文件中更近的位置。

本书中讨论的许多优化属于多个类别。例如，我们可以说向量化是并行化和批处理的组合；而循环阻塞（分块）是批处理和消除冗余工作的体现。

为了完整起见，让我们也列出其他可能明显但仍然相当合理的加速方式：

* **用另一种语言重写代码**：如果程序是用解释型语言（Python、JavaScript 等）编写的，将其性能关键部分用开销较低的语言重写，例如 C++、Rust、Go 等。
* **调整编译器选项**：检查你是否至少使用了这三个编译器标志：`-O3`（启用与机器无关的优化）、`-march`（启用针对特定 CPU 架构的优化）、`-flto`（启用过程间优化）。但不要止步于此；还有许多其他影响性能的选项。我们将在后面的章节中研究其中一些。你可以考虑为应用程序挖掘最佳选项集；可以使用自动化此过程的商业产品。
* **优化第三方软件包**：绝大多数软件项目都利用了专有和开源代码层。这包括操作系统、库和框架。你可以通过替换、修改或重新配置其中一个部分来寻求改进。
* **购买更快的硬件**：显然，这是一个带有相关成本的商业决策，但有时当其他选项已经用尽时，它是提高性能的唯一方法。当你识别出应用程序中的性能瓶颈并清楚地与高层管理人员沟通时，更容易证明购买的合理性。例如，一旦你发现内存带宽限制了多线程程序的性能，你可能会建议购买具有更多内存通道和 DIMM 插槽的服务器主板和处理器。

### 算法优化 {.unlisted .unnumbered}

标准算法和数据结构并不总是对性能关键型工作负载有效。例如，传统上，链表的每个新节点都是动态分配的。除了可能调用许多昂贵的内存分配之外，这还可能导致列表的所有元素分散在内存中。遍历这样的数据结构对缓存不友好。即使算法复杂度仍然是 O(N)，但实际上时间会比普通数组差得多。一些数据结构，如二叉树，具有自然的类似链表的表示，因此用指针追逐方式实现它们可能是诱人的。然而，存在更高效的"扁平"版本的数据结构，例如 `boost::flat_map` 和 `boost::flat_set`。

在为手头的问题选择算法时，你可能会快速选择最流行的选项并继续前进……即使它可能不是你特定情况下的最佳选择。假设你需要在排序数组中找到一个元素。大多数开发人员考虑的第一个选项是二分查找，对吧？它非常著名，并且在算法复杂度 O(logN) 方面是最优的。如果我告诉你数组保存 32 位整数值，并且数组大小通常很小（少于 20 个元素），你会改变决定吗？最终，测量应该指导你的决定，但二分查找遭受分支预测错误，因为每个元素值的测试都有 50% 的概率为真。这就是为什么在小数组上，线性扫描通常更快，尽管它的算法复杂度更差。[^1]
