## 分支记录机制 {#sec:lbr}

现代高性能 CPU 提供分支记录机制，使处理器能够持续记录一组先前执行的分支。但在深入细节之前，你可能会问：为什么我们对分支如此感兴趣？因为这是我们确定程序控制流的方式。我们基本上忽略基本块（参见 [@sec:BasicBlock]）中的其他指令，因为分支总是基本块中的最后一条指令。由于基本块中的所有指令都保证执行一次，我们只能关注将"代表"整个基本块的分支。因此，如果我们可以跟踪每个分支的结果，就可以重建程序的整个逐行执行路径。这就是 Intel 处理器跟踪（PT）功能能够做到的，在附录 C 中讨论。我们将在本节讨论的分支记录机制基于采样，而不是跟踪，因此具有不同的用例和能力。

Intel、AMD 和 Arm 设计的处理器都宣布了它们的分支记录扩展。确切的实现可能不同，但思想是相同的：硬件在执行程序的同时记录每个分支的"from"和"to"地址以及一些附加数据。如果我们收集足够长的源-目标对历史，我们将能够展开程序的控制流，就像调用栈一样，但深度有限。此类扩展旨在对运行中的程序造成最小的减速（通常在 1% 以内）。

有了分支记录机制，我们可以在分支（或周期，这不重要）上采样，但在每个样本期间，查看先前执行的 N 个分支。这为我们提供了热代码路径中控制流的合理覆盖，但不会因为太多信息而不堪重负，因为只检查了少量的总分支。重要的是要记住这仍然是采样，因此并非每个执行的分支都可以被检查。CPU 通常运行得太快，无法做到这一点。

重要的是要记住，只有被采取的分支才会被记录。[@lst:LogBranches] 显示了分支结果如何被跟踪的示例。此代码表示一个具有三条可能改变程序执行路径的指令的循环，即循环回边 `JNE` (1)、条件分支 `JNS` (2)、函数 `CALL` (3) 和从此函数返回的地址 (4)。

Listing: 记录分支的示例。

~~~~ {#lst:LogBranches .asm}
----> 4eda10:  mov   edi,DWORD PTR [rbx]
|     4eda12:  test  edi,edi
| --- 4eda14:  jns   4eda1e              <== (2)
| |   4eda16:  mov   eax,edi
| |   4eda18:  shl   eax,0x7
| |   4eda1b:  lea   edi,[rax+rdi*8]
| └─> 4eda1e:  call  4edb26              <== (3)
|     4eda23:  add   rbx,0x4             <== (4)
|     4eda27:  mov   DWORD PTR [rbx-0x4],eax
|     4eda2a:  cmp   rbx,rbp
----- 4eda2d:  jne   4eda10              <== (1)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

[@lst:BranchHistory] 显示了使用分支记录机制可以记录的一个可能的分支历史。它显示了在执行 `CALL` 指令时最后 7 个分支结果（未显示更多）。因为在循环的最新迭代中，`JNS` 分支（`4eda14` &rarr; `4eda1e`）未被采取，所以它没有被记录，因此不出现在历史中。
