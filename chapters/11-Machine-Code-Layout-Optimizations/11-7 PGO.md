## 配置文件引导优化 {#sec:secPGO}	

编译程序并生成最优汇编完全依赖于启发式方法。代码转换算法有许多边缘情况，旨在在特定情况下实现最佳性能。对于编译器做出的许多决策，它都尝试根据某些典型情况猜测最佳选择。例如，在决定是否应内联特定函数时，编译器可以考虑该函数将被调用的次数。问题是编译器事先不知道这一点。它首先需要运行程序来了解。没有任何运行时信息，编译器将不得不猜测。

这就是配置文件信息变得有用的时候。有了配置文件信息，编译器可以做出更好的优化决策。大多数编译器中有一组转换可以根据提供给它们的配置文件数据调整其算法。这组转换称为配置文件引导优化（PGO）。当配置文件数据可用时，编译器可以使用它来指导优化。否则，它将退回到使用其标准算法和启发式方法。有时在文献中，你可以找到反馈引导优化（FDO）一词，它与 PGO 指的是同一件事。

图 @fig:PGO_flow 显示了使用 PGO 的传统工作流程，也称为*检测 PGO*。首先，你编译程序并告诉编译器自动检测代码。这将向函数中插入一些簿记代码以收集运行时统计信息。第二步是使用代表应用程序典型工作负载的输入数据运行检测后的二进制文件。这将生成配置文件数据，一个包含运行时统计信息的新文件。它是一个原始转储文件，包含有关函数调用次数、循环迭代次数和其他基本块命中次数的信息。此工作流中的最后一步是使用配置文件数据重新编译程序以生成优化的可执行文件。

![检测 PGO 工作流。](../../img/cpu_fe_opts/pgo_flow.png){#fig:PGO_flow width=100% }

开发人员可以通过使用 `-fprofile-instr-generate` 选项构建程序来在 LLVM 编译器中启用 PGO 检测（步骤 1）。这将指示编译器添加检测代码以在运行时收集配置文件信息。此类信息通常包括我们进入程序中每个基本块的次数。

之后，LLVM 编译器可以使用 `-fprofile-instr-use` 选项使用配置文件数据重新编译程序并输出 PGO 调优的二进制文件。在 Clang 中使用 PGO 的指南在[文档](https://clang.llvm.org/docs/UsersManual.html#profiling-with-instrumentation)中描述。[^7] GCC 编译器使用不同的选项集：`-fprofile-generate` 和 `-fprofile-use`，如[文档](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html#Optimize-Options)中所述。[^10]

PGO 帮助编译器改善函数内联、代码放置、寄存器分配和其他代码转换。PGO 主要用于具有大代码库的项目，例如 Linux 内核、编译器、数据库、Web 浏览器、视频游戏、生产力工具等。对于具有数百万行代码的应用程序，它是改善机器代码布局的唯一实用方法。

并非所有工作负载都能从 PGO 中受益。具有严重前端瓶颈的工作负载可能通过使用 PGO 看到高达 30% 的加速。但是，计算受限的工作负载（如科学计算）可能看不到任何好处。

虽然一些软件项目将检测 PGO 作为其构建过程的一部分采用，但采用率仍然非常低。有几个原因。主要原因是检测可执行文件的巨大运行时开销。运行检测后的二进制文件并收集配置文件数据通常会带来 5-10 倍的减速，这使得构建步骤更长，并阻止直接从生产系统（无论是客户端设备还是云中）收集配置文件。不幸的是，你不能收集一次配置文件数据并将其用于所有未来的构建。随着应用程序源代码的发展，配置文件数据变得过时（不同步）并需要重新收集。

PGO 流程中的另一个注意事项是，编译器应该只使用代表性的场景来训练你的应用程序的使用方式。否则，你可能会降低程序的性能。编译器"盲目地"使用你提供的配置文件数据。它假设程序将始终以相同的方式运行，无论输入数据是什么。PGO 的用户应小心选择用于收集配置文件数据（步骤 2）的输入数据，因为在改进应用程序的一个用例的同时，其他用例可能会被优化。幸运的是，它不必是完全单一的工作负载，因为来自不同工作负载的配置文件数据可以合并以代表应用程序的一组用例。

2016 年，Google 率先提出了基于采样的 PGO 的替代解决方案。[@AutoFDO] 不是检测代码，而是可以从标准分析工具（如 Linux `perf`）的输出中获取配置文件数据。Google 开发了一个名为 [AutoFDO](https://github.com/google/autofdo)[^8] 的开源工具，将 Linux `perf` 生成的采样数据转换为 GCC 和 LLVM 等编译器可以理解的格式。

这种方法比检测 PGO 有几个优势。首先，它从 PGO 构建工作流中消除了一个步骤，即步骤 1，因为不需要构建检测后的二进制文件。其次，配置文件数据收集在已优化的二进制文件上运行，因此运行时开销要低得多。这使得在生产环境中更长时间地收集配置文件数据成为可能。由于此方法基于硬件收集，它还启用了使用检测 PGO 不可能实现的新优化。一个例子是分支到 cmov 转换，这是一种将条件跳转替换为条件移动以避免分支预测错误成本的转换（参见 [@sec:BranchlessSelection]）。为了有效地执行此转换，编译器需要知道原始分支被预测错误的频率。此信息在现代 CPU（Intel Skylake+）上通过基于采样的 PGO 可用。

2018 年中期，Meta 开源了其二进制优化工具 [BOLT](https://code.fb.com/data-infrastructure/accelerate-large-scale-applications-with-bolt/)[^9]，它适用于已编译的二进制文件。它首先反汇编代码，然后使用采样分析器（如 Linux `perf`）收集的配置文件信息进行各种布局转换，然后重新链接二进制文件。[@BOLT] 截至今天，BOLT 有超过 15 个优化传递，包括基本块重排序、函数分割和重排序等。与传统 PGO 类似，BOLT 优化的主要候选者是遭受指令缓存和 ITLB 未命中的程序。自 2022 年 1 月以来，BOLT 已成为 LLVM 项目的一部分，并作为独立工具可用。

BOLT 引入几年后，Google 开源了其二进制重链接工具 [Propeller](https://github.com/google/llvm-propeller/blob/plo-dev/Propeller_RFC.pdf)。它服务于类似的目的，但它不是反汇编原始二进制文件，而是依赖于链接器输入，因此可以分布在多台机器上以获得更好的扩展性和更少的内存消耗。Post-link 优化器（如 BOLT 和 Propeller）可以与传统 PGO（和链接时优化）结合使用，通常提供额外的 5-10% 的性能加速。此类技术开启了基于硬件遥测的新型二进制重写优化。
