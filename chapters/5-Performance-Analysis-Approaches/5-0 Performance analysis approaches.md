# 性能分析方法 {#sec:sec_PerfApproaches}

当你正在进行高级优化时，例如将更好的算法集成到应用程序中，通常很容易判断性能是否提高，因为基准测试结果通常是显著的。大的加速，如 2 倍、3 倍等，从性能分析的角度来看相对明显。当你从程序中消除大量计算时，你期望看到运行时间的明显差异。

但是，也有这样的情况：你看到执行时间有很小的变化，比如 5%，但你不知道它来自哪里。仅靠计时或吞吐量测量无法解释性能上升或下降的原因。在这种情况下，我们需要更多关于程序如何执行的见解。这就是我们需要进行性能分析来理解我们观察到的减速或加速的底层性质的情况。

性能分析类似于侦探工作。要解决性能谜团，你需要收集所有可用的数据并尝试形成假设。一旦做出假设，你就设计一个实验来证明或反驳它。在你找到线索之前，它可能会来回几次。就像一个好侦探一样，你试图收集尽可能多的证据来确认或反驳你的假设。一旦你有了足够的线索，你就可以对你观察到的行为做出令人信服的解释。

当你刚开始处理性能问题时，你可能只有测量结果，例如代码更改前后的结果。根据这些测量，你得出结论程序变慢了 `X`%。如果你知道减速发生在某个提交之后，这可能已经给了你足够的信息来修复问题。但如果你没有好的参考点，那么减速的可能原因是无穷无尽的，你需要收集更多数据。收集此类数据最受欢迎的方法之一是分析应用程序并查看热点。本章介绍了这种方法以及其他几种已被证明在性能工程中有用的数据收集方法。

下一个问题是："有哪些可用的性能数据以及如何收集它们？"堆栈的硬件和软件层都有设施来跟踪性能事件并在程序运行时记录它们。在这个上下文中，硬件是指执行程序的 CPU，软件是指操作系统、库、应用程序本身以及用于分析的其他工具。通常，软件堆栈提供高级指标，如时间、上下文切换次数和页面错误，而 CPU 监控缓存未命中、分支预测错误和其他与 CPU 相关的事件。根据你要解决的问题，某些指标比其他指标更有用。因此，这并不意味着硬件指标总是能给我们提供更精确的程序执行概述。它们只是不同。例如，某些指标（如上下文切换次数）无法由 CPU 提供。性能分析工具（如 Linux `perf`）可以同时使用来自操作系统和 CPU 的数据。

正如你可能猜测的那样，性能工程师可能使用数百种数据源。本章主要关于收集硬件级信息。我们将介绍一些最流行的性能分析技术：代码检测、跟踪、表征、采样和 Roofline 模型。我们还讨论不涉及运行实际应用程序的静态性能分析技术和编译器优化报告。
